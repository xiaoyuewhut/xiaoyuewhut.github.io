# 端到端自动驾驶模块输入输出

# 绪论

## 端到端概念

现在主流所谓“端到端自动驾驶”，大多数不是“图像/雷达到油门刹车方向盘”的纯黑盒，而是“从传感器到规划轨迹端到端训练”，内部仍然显式分成感知表征、预测、规划、控制/安全约束等模块，只是这些模块用共享 backbone、query/token、可微训练目标连接起来。

典型的端到端模型有如下几种：

1. **狭义端到端**：<span style="background-color: rgba(255, 246, 122, 0.8);">传感器输入直接输出控制量</span> `steer/throttle/brake`。

这类最像大家直觉里的端到端，但公开研究里反而不是主流，因为控制信号太低层、可解释性和安全约束弱。典型如 TCP 里有 direct control branch，但它仍然和 trajectory branch 融合。

1. **规划端到端**：传感器输入输出<span style="background-color: rgba(255, 246, 122, 0.8);">未来轨迹/waypoints</span>，最后由 PID/MPC/车辆控制器执行。

这是当前开源学术界<span style="background-color: rgba(255, 246, 122, 0.8);">最主流</span>：TransFuser、UniAD、VAD、SparseDrive、DiffusionDrive、GenAD 大多属于这类。

1. **模块化但端到端训练**：内部仍有检测、跟踪、地图、运动预测、占用预测、规划等模块，但整体是一张网络/一套训练目标。

UniAD 论文明确把 tracking、mapping、motion、occupancy、planning 串成一个 planning-oriented 网络，用 query 作为模块接口；它不是传统手工 pipeline，但也不是无模块黑盒。UniAD 论文/仓库说明其“perception, prediction and planning tasks hierarchically”集成在一个框架里。[UniAD GitHub](https://github.com/OpenDriveLab/UniAD)、[CVPR paper](https://openaccess.thecvf.com/content/CVPR2023/papers/Hu_Planning-Oriented_Autonomous_Driving_CVPR_2023_paper.pdf)

1. **VLA/世界模型式端到端**：把语言、动作、视频生成/世界模型引入驾驶。

例如 Wayve LINGO-2 用连续相机帧 token、route、当前速度、限速等条件，预测驾驶轨迹和文本解释，控制器再执行轨迹；GAIA-1/2 更偏世界模型，用视频、文本、动作生成未来驾驶场景，不等价于直接控制器。[Wayve LINGO-2](https://wayve.ai/thinking/lingo-2-driving-with-language/)、[GAIA-1](https://arxiv.org/abs/2309.17080)

从接口看，nuScenes 系模型多输出未来 3 秒左右的 `6 x 2` 二维轨迹；NAVSIM/DiffusionDrive 输出 `8 x 3` 的 SE2 pose 序列；CARLA 系模型通常输出二维 waypoints，再由控制器转换为车辆控制量。

# DiffusionDrive / NAVSIM

## 输入

输入分 3 类：

```plaintext
camera_feature
lidar_feature
status_feature
```

`camera_feature` 是图像输入。代码里取左前、正前、右前三路相机，裁剪后横向拼接，把它们横向拼成一张很宽的前视图，然后用图像缩放函数把这张拼接图统一变成 `1024` 像素宽、`256` 像素高。

这么做的原因是神经网络通常要求输入图像尺寸固定。无论原始相机图像多大，最后都变成同一个大小，方便送进 CNN/Transformer。

`lidar_feature` 是 LiDAR 点云转成的 BEV histogram。可以理解为俯视图栅格，每个格子统计点云密度。默认范围约为自车周围 `[-32,32]m x [-32,32]m`，分辨率 `0.25m`，得到 `256 x 256` 的 BEV 图。（一张点云占据/密度图，不含语义信息，本身不知道这个点是车、行人、路面还是护栏。）

`status_feature` 是 8 维低维状态：

```plaintext
status_feature = concat([
    driving_command,   # 4 维
    ego_velocity,      # 2 维
    ego_acceleration,  # 2 维
])
```

也就是

```plaintext
[
  command_left,
  command_straight,
  command_right,
  command_unknown,
  v_x,
  v_y,
  a_x,
  a_y
]
```

`driving_command` 是路线意图，不是控制量。它告诉模型导航希望往左、直行、往右，还是未知。

例如：

```plaintext
[0, 1, 0, 0] = 期望沿路线直行
[1, 0, 0, 0] = 期望向左
[0, 0, 1, 0] = 期望向右
[0, 0, 0, 1] = 路线意图未知
```

全局导航可能长这样：

```plaintext
从 A 到 B：
先沿当前路走 300m
进入环岛
第二个出口驶出
靠右并入主路
500m 后左转
再直行 2km
```

但端到端模型每一帧只负责预测未来几秒，比如未来 3 秒或 4 秒的轨迹。对这几秒来说，它不需要知道完整 A 到 B 的所有路径细节，只需要知道当前局部决策：

```plaintext
这个路口走左侧分支
这个岔路保持右侧
这个车道继续直行
这个环岛准备从右前方出口出去
```

所以 `driving_command` 是一种**局部路线提示**，不是完整路径。可以理解成两层：

```plaintext
全局路径：
一条连续的、可能弯曲的 route polyline

局部 command：
从这条 route 上抽出来的短时意图，比如 left / right / straight
```

`ego_velocity=[v_x,v_y]` 是自车在局部坐标系下的速度分量，不是单个速度大小。`ego_acceleration=[a_x,a_y]` 同理，是局部坐标下的加速度分量。

## 中间输出

- `agent_states`: 最多 `30` 个车，格式 `[x, y, heading, length, width]`。
- `bev_semantic_map`: 7 类 BEV 语义图，范围来自 `[-32,32]m x [-32,32]m`，像素分辨率 `0.25m`。

`bev_semantic_map` 是语义图。它表达的是每个 BEV 栅格属于什么类别，比如 DiffusionDrive 代码里大致有这些类别：

```plaintext
0 = background
1 = road / lane / intersection
2 = walkway
3 = centerline
4 = static objects
5 = vehicles
6 = pedestrians
```

## 输出

- `trajectory_sampling = TrajectorySampling(time_horizon=4, interval_length=0.5)`，所以是 `8` 个未来点。
- 多模态候选：`poses_reg: [B, 20, 8, 3]`
- 每个 pose 是：`[x, y, heading]`
- mode 分数：`poses_cls: [B, 20]`
- 最终输出：取最高分 mode，`trajectory: [B, 8, 3]`

```plaintext
poses_reg: [B, 20, 8, 3]
poses_cls: [B, 20]
trajectory: [B, 8, 3]
```

含义是：先生成 20 条候选轨迹，每条轨迹有 8 个未来 pose，每个 pose 是：

```plaintext
[x, y, heading]
```

`x,y` 是未来自车相对当前自车坐标系的位置，`heading` 是未来朝向角。时间上是未来 4 秒，每 0.5 秒一个点。最后按 `poses_cls` 选择分数最高的候选轨迹作为最终输出。

## 问题

### 只有 8 个 pose 交给控制器会不会太稀疏了？

会有点稀疏，但这在这些公开 benchmark 里是正常设定。**模型输出的 8 个点通常不是直接逐点硬执行，而是作为短时参考轨迹，再由控制器插值、平滑或用 PID/MPC/LQR 跟踪**。

benchmark 主要看未来轨迹误差、碰撞、可行性等。但如果真上车控制，控制器一般不会只在 0.5 秒更新一次。它会在更高频率运行，比如 20Hz、50Hz、100Hz，然后在这 8 个点之间做：

- 插值
- 曲线拟合
- 速度规划
- 横纵向控制
- 碰撞/舒适性约束

### 传感器适配

DiffusionDrive 的“3 个前视摄像头 + LiDAR BEV”只是 NAVSIM 数据集/公开代码的输入格式。量产车如果是小鹏 G9、理想 L9、蔚来 ET7、问界 M9 这种配置，ADAS 传感器会有很多，工程上通常不会把图像简单横向拼接，而是更可能**把不同传感器配置先适配成统一的中间表示，再接规划模型。**

比如：

- BEV feature
- occupancy grid
- agent tokens
- map tokens
- lane graph
- local route polyline

不是原始地规定“必须是三路前视相机 + LiDAR”。

# VAD

VAD 是 camera-only，输入多相机历史帧，常见配置里 `queue_length=4`，即用连续 4 帧图像形成时序 BEV。它还使用 `can_bus`、自车历史轨迹、未来导航命令等元信息。

它的端到端更准确说是：**多相机图像 → BEV 表征 → 检测/地图/运动预测/自车规划联合输出**。

```plaintext
6相机 x 4帧图像 + can_bus / ego history / command
        ↓
ResNet-FPN + BEVFormer encoder
        ↓
BEV feature: [B, 200*200, 256]
        ↓
object queries → 3D boxes + agent future trajectories
map queries    → vectorized map lines
ego query      → ego future trajectories
        ↓
ego_fut_preds: [B, 3, 6, 2]
```

所以 VAD 的本质接口是：**输入多相机时序图像和自车状态，输出检测框、地图向量、agent 多模态未来轨迹，以及 ego 的 3 模式二维规划轨迹**。它的端到端是“图像到规划轨迹，并把感知、预测、地图、规划一起训练”。

## 输入

- 多相机图像，camera-only。
- `queue_length = 4`，即输入 4 帧历史序列。
- BEV 网格：`bev_h = 200, bev_w = 200`。
- 点云/BEV范围配置：`[-15, -30, -2, 15, 30, 2]`，虽然模型用 camera，但 BEV 坐标范围按这个定义。

```plaintext
img: [queue_length, num_cam, C, H, W]
```

图像经过 normalize、scale、pad 后进入 ResNet + FPN，再由 BEVFormer 风格 encoder 转成 BEV feature。

同时数据包里还带这些非图像字段：

```plaintext

ego_his_trajs
ego_fut_trajs
ego_fut_masks
ego_fut_cmd
ego_lcf_feat
gt_bboxes_3d
gt_labels_3d
gt_attr_labels
```

## BEV 表征

VAD 的核心中间表示是 BEV：

```plaintext
bev_h = 200
bev_w = 200
embed_dims = 256
```

所以可以理解为模型把 6 相机、4 帧图像投到一个 `200 x 200` 的鸟瞰特征网格上，每个格子是 256 维特征。BEV 的物理范围由配置给出：

```plaintext
point_cloud_range = [-15, -30, -2, 15, 30, 2]
```

大致表示自车坐标系附近：

- x 方向：`-15m ~ 15m`
- y 方向：`-30m ~ 30m`

## 目标检测

VAD 仍然有目标检测输出：

```plaintext
all_cls_scores
all_bbox_preds
```

其中：

- `all_cls_scores`：每个 object query 的类别分数；
- `all_bbox_preds`：每个 object query 的 3D box；
- `num_query = 300`，即最多用 300 个 object query 表达动态/静态目标候选；
- 类别是 nuScenes 10 类，例如 car、truck、bus、pedestrian、traffic_cone 等。

> 🫡 说明 VAD 不是跳过感知模块，它把检测作为联合任务一起训练。

## **地图输出**

VAD 的地图不是 raster map，而是 vector map。配置：

```plaintext
map_classes = ["divider", "ped_crossing", "boundary"]
map_num_vec = 100
map_num_pts_per_vec = 20
```

输出大致是：

```plaintext
map_all_cls_scores
map_all_pts_preds
map_all_bbox_preds
```

含义：

```plaintext
map_all_pts_preds: [decoder_layer, B, 100, 20, 2]
```

简化看就是：

```plaintext
[B, 100, 20, 2]
```

也就是：

- 最多预测 100 条地图向量；
- 每条向量 20 个采样点；
- 每个点是 `[x,y]`；
- 类别是 divider / pedestrian crossing / boundary。

所以 VAD 的 map module 输出是可直接给规划模块用的二维矢量线。

## **agent 运动预测输出**

VAD 对检测到的 agent 预测未来轨迹。配置：

```plaintext
fut_ts = 6
fut_mode = 6
```

输出：

```plaintext
agent_fut_preds: [B, num_agent, fut_mode, fut_ts, 2]
agent_fut_cls_scores: [B, num_agent, fut_mode]
```

展开就是：

```plaintext
[B, num_agent, 6, 6, 2]
```

含义：

- 每个 agent 有 6 种未来可能；
- 每种未来有 6 个时间步；
- 每个时间步是 `[x,y]`；
- `agent_fut_cls_scores` 给这 6 种未来 mode 打分。

这里不直接输出 agent 的 yaw、速度、加速度。训练时很多轨迹量按位移/增量处理，再通过 `cumsum` 变成累计位置。

## **ego 规划输出**

这是 VAD 最关心的输出。配置：

```plaintext
ego_fut_mode = 3
fut_ts = 6
```

输出：

```plaintext
ego_fut_preds: [B, 3, 6, 2]
```

含义：

- `3`：三种高层驾驶命令 mode；
- `6`：未来 6 个时间点；
- `2`：每个点是 `[x,y]`。

也就是：

```plaintext
ego_fut_preds[b, mode, t] = [x_t, y_t]
```

它没有：

- heading；
- speed；
- acceleration；
- throttle；
- brake；
- steer。

`ego_fut_cmd: [B,3]` 是 one-hot，用于告诉训练时当前样本应该监督哪一个 mode。例如只对 `ego_fut_cmd == 1` 的那条 ego 轨迹计算规划 loss。

**规划 loss 用到什么?**

VAD 的规划 loss 不只做 L1 拟合，还包含约束项：

```plaintext
loss_plan_reg    # 轨迹回归
loss_plan_bound  # 与地图边界/道路边界相关
loss_plan_col    # 与 agent 碰撞相关
loss_plan_dir    # 与地图方向相关
```

这说明它虽然输出二维轨迹，但规划不是纯粹模仿 ground truth。它还会用预测出来的：

- agent 位置/未来轨迹；
- map vector；
- agent score；
- map score；

去约束 ego 轨迹不要碰撞、不要越界、方向尽量合理。

# UniAD

UniAD 比 VAD 更像一个任务链条被神经网络化的系统。它把 **感知、跟踪、地图、运动预测、占用预测、规划** 串成一个 planning-oriented 框架。每个模块之间传的不是传统工程模块的 JSON/ROS 消息，而是 query、BEV feature、mask、trajectory tensor 这些神经网络接口。

## 输入

UniAD 的基础输入是 nuScenes 多相机历史帧：

```plaintext
img: [queue_length, 6, 3, H, W]
queue_length = 3
```

也就是连续 3 帧、6 个相机。配置里 BEV 尺寸是：

```plaintext
bev_h = 200
bev_w = 200
embed_dim = 256
```

图像经过 ResNet-101 + FPN + BEVFormer 类 encoder，形成：

```plaintext
bev_embed: [B, 200*200, 256]
```

可以理解为一个 `200 x 200` 的鸟瞰特征图，每个格子是 256 维。

训练数据还会带很多监督字段：

```plaintext
gt_bboxes_3d
gt_labels_3d
gt_inds
gt_fut_traj
gt_fut_traj_mask
gt_past_traj
gt_past_traj_mask
gt_sdc_bbox
gt_sdc_label
gt_sdc_fut_traj
gt_sdc_fut_traj_mask
gt_lane_labels
gt_lane_bboxes
gt_lane_masks
gt_segmentation
gt_instance
gt_flow
gt_future_boxes
sdc_planning
sdc_planning_mask
command
```

这里的 `sdc` 是 self-driving car，也就是自车。<br/>UniAD 可以写成：

```plaintext
multi-camera history
        ↓
BEV encoder
        ↓
Track Head
        ↓
Map / Panoptic Seg Head
        ↓
Motion Head
        ↓
Occupancy Head
        ↓
Planning Head
        ↓
sdc_traj: [B, 6, 2]
```

它的关键点是：<span style="background-color: rgba(255, 246, 122, 0.8);">planning head 不直接吃原始图像，而是吃 motion head 和 occupancy head 的输出</span>。

## **Track Head：检测与跟踪**

Track head 负责从 BEV 中得到动态目标的 tracking query 和检测框。配置里：

```plaintext
num_query = 900
num_classes = 10
```

输出里关键字段包括：

```plaintext
track_query_embeddings
track_query_matched_idxes
track_bbox_results
sdc_embedding
sdc_track_bbox_results
```

含义：

- `track_query_embeddings`：每个被跟踪目标的 query 表示；
- `track_bbox_results`：目标检测/跟踪框；
- `track_query_matched_idxes`：query 和 GT object 的匹配关系；
- `sdc_embedding`：自车的专用 query；
- `sdc_track_bbox_results`：自车伪框。

这里很重要：UniAD 会把自车也当成一个特殊目标，拼进后续 motion head。这样 motion 模块可以同时处理其他 agent 和自车。

## **Map / Seg Head：道路结构表示**

UniAD 的地图部分不像 VAD 那样主要输出固定数量 vector map，它有 BEV segmentation / panoptic segmentation 风格的表示。训练字段包括：

```plaintext
gt_lane_labels
gt_lane_bboxes
gt_lane_masks
```

输出主要给 motion head 提供：

```plaintext
lane_query
lane_query_pos
args_tuple
```

也就是道路/车道相关 query。Motion head 会用这些 lane query 参与 agent 未来轨迹预测。

## **Motion Head：agent 与自车运动预测**

Motion head 是 UniAD 的核心中间接口之一。配置：

```plaintext
predict_steps = 12
predict_modes = 6
```

输出：

```plaintext
all_traj_scores
all_traj_preds
traj_query
track_query
track_query_pos
```

典型含义：

```plaintext
all_traj_preds: [num_decoder, B, num_agent, 6, 12, ?]
all_traj_scores: [num_decoder, B, num_agent, 6]
```

代码中每个 agent 有 6 个未来 mode，12 个未来步。轨迹先预测增量，再 `cumsum` 成累计轨迹。轨迹状态经过 `bivariate_gaussian_activation`，所以 motion 预测不是纯 `[x,y]`，而是带概率分布参数的轨迹表达。论文/代码里的 trajectory loss 主要使用位置部分计算 minADE、minFDE、miss rate 等。

自车的处理更特殊。Motion head 会先把自车 query 拼到 agent query 最后：

```plaintext
track_query = concat(agent_track_query, sdc_embedding)
gt_fut_traj = concat(agent_gt_fut_traj, gt_sdc_fut_traj)
```

然后 motion head 输出后，再把自车拆出来：

```plaintext
sdc_traj_query: [num_dec, B, 6, 256]
sdc_track_query: [B, 256]
sdc_track_query_pos: [B, 256]
```

这里的 `6` 是自车未来运动的 mode 数。也就是说，planning head 拿到的不是 motion head 的最终 `[x,y]` 轨迹，而是 **自车未来 motion query**。

## **Occupancy Head：未来占用预测**

Occupancy head 用 motion/track query 和 BEV feature 预测未来占用。配置：

```plaintext
occ_n_future = 4
```

但输出包含当前帧，所以常见是：

```plaintext
seg_out: [B, 5, 1, 200, 200]
ins_seg_out: [B, 5, 200, 200]
```

含义：

- `5 = 当前帧 + 未来 4 帧`；
- `seg_out` 是 BEV 栅格占用；
- `ins_seg_out` 是实例级占用分割；
- 栅格大小是 `200 x 200`。

occupancy 的作用是给 planning 阶段提供碰撞/可行性信息。测试时 planning head 可以用 `occ_mask` 做 collision optimization。

## **Planning Head：最终自车规划**

Planning head 的输入是：

```plaintext
bev_embed
bev_pos
sdc_traj_query
sdc_track_query
command
occ_mask
```

字段含义：

- `bev_embed`：整场景 BEV 特征；
- `bev_pos`：BEV 位置编码；
- `sdc_traj_query`：motion head 输出的自车未来运动 query；
- `sdc_track_query`：自车当前跟踪 query；
- `command`：导航命令；
- `occ_mask`：occupancy head 输出的未来占用，用于测试时碰撞优化。

`command` 是 3 类整数，不是 4 维 one-hot。代码里根据自车未来规划终点横向偏移生成：

```plaintext
0 = RIGHT
1 = LEFT
2 = FORWARD
```

Planning head 先拼接：

```plaintext
plan_query = concat(sdc_traj_query, sdc_track_query, navi_embed)
```

然后做一次 transformer attention 到 BEV feature，最后输出：

```plaintext
sdc_traj_all: [B, 6, 2]
sdc_traj: [B, 6, 2]
```

代码里最后一层是：

```plaintext
Linear(256, planning_steps * 2)
planning_steps = 6
```

所以最终规划接口就是：

```plaintext
6 个未来点，每个点 [x, y]
```

它不直接输出：

- heading；
- velocity；
- acceleration；
- steer；
- throttle；
- brake。

虽然训练标签 `sdc_planning` 里是：

```plaintext
[1, 6, 3] = [x, y, yaw]
```

但 loss 的 ADE 主要拿预测的 `[x,y]` 和标签的 `[:2]` 比较。yaw 更多用于构造标签、碰撞相关计算或 future box 约束，不是 planning head 的直接输出字段。

## **时间尺度**

UniAD 的 planning 输出：

```plaintext
planning_steps = 6
```

nuScenes 常用采样间隔是 0.5 秒，所以这 6 个点通常对应未来 3 秒：

```plaintext
0.5s, 1.0s, 1.5s, 2.0s, 2.5s, 3.0s
```

Motion head 的 agent 预测更长：

```plaintext
predict_steps = 12
```

通常对应未来 6 秒。

所以 UniAD 里有两个不同 horizon：

- agent motion prediction：12 步，约 6 秒；
- ego planning：6 步，约 3 秒。

**和 VAD 的关键区别**<br/>VAD 最终 ego 输出是：

```plaintext
ego_fut_preds: [B, 3, 6, 2]
```

它直接给 3 个导航 mode 的 ego 轨迹。

UniAD 最终 ego 输出是：

```plaintext
sdc_traj: [B, 6, 2]
```

它是单条轨迹。导航命令不是作为 3 条轨迹 mode 输出，而是作为 `navi_embed` 输入进 planning head，模型根据 command 生成一条轨迹。

更具体地说：

```plaintext
VAD: 输出多个 ego command mode，然后用 ego_fut_cmd 选择/监督
UniAD: 输入 command embedding，直接输出对应 command 的单条 ego trajectory
```

## **总结**

UniAD 的输入输出可以压缩成下面这条链：

```plaintext
输入:
  3 帧 x 6 相机图像 + ego pose / 时间 / GT boxes / GT future traj / lane mask / occupancy GT / command

中间:
  bev_embed: [B, 40000, 256]
  track_query: 目标跟踪 query
  lane_query: 道路结构 query
  traj_query: agent 多模态运动 query
  sdc_traj_query: 自车运动 query
  occ_mask: [B, 5, 1, 200, 200]

最终:
  sdc_traj: [B, 6, 2]
  每个点是局部坐标系下的 [x, y]
```

所以 UniAD 保留了非常明确的中间接口，只是这些接口主要是 query、BEV feature、occupancy mask 和 trajectory tensor，而不是传统工程模块里的显式对象列表。

# GenAD

GenAD 可以看作 VAD 路线上的生成式扩展。它仍然使用多相机历史帧和 BEV/query 表示，但不再只把未来轨迹当成普通回归目标，而是把 ego 和 agent 的未来状态放进 latent trajectory space 里生成。最终对外的规划接口仍然和 VAD 接近：ego 输出 3 个命令 mode，每个 mode 6 个二维未来点。

> 💡 GenAD 的“生成式”主要改变内部建模方式，不改变最终控制接口。它最终仍然输出未来 `[x,y]` 轨迹点，不直接输出方向盘、油门、刹车。

## 输入

GenAD 使用 nuScenes 风格的 camera-only 输入。配置里多相机图像经过 ResNet-FPN 和 BEVFormer 类 encoder，形成 BEV 表征。典型输入可以概括为：

```plaintext
多相机历史帧
+ can_bus / ego history / command
+ agent 3D box 监督
+ agent future trajectory 监督
+ map vector 监督
```

## 中间表示

GenAD 的中间表示和 VAD 一样包含 agent query、map query、ego query，但它额外引入生成式分布建模。代码中可以看到 `latent_dim = 32`，并使用 probabilistic loss 约束生成分布。

```plaintext
multi-camera images
        ↓
BEV encoder
        ↓
agent queries + map queries + ego query
        ↓
future distribution / latent trajectory generation
        ↓
agent future trajectories + ego future trajectories
```

这里的 latent trajectory space 可以理解为：模型不是只针对每个目标单独回归一串点，而是学习一个能同时解释 ego 和周围 agent 未来运动的隐变量空间。这样做的目标是提高多主体交互场景下的未来轨迹一致性。

## agent 输出

GenAD 对周围 agent 的未来输出为：

```plaintext
agent_fut_preds: [B, num_agent, fut_mode, fut_ts, 2]
agent_fut_cls_scores: [B, num_agent, fut_mode]
```

展开后就是：

```plaintext
[B, num_agent, 6, 6, 2]
```

含义是：每个 agent 有 6 条候选未来轨迹，每条轨迹有 6 个未来时间步，每个时间步是二维坐标 `[x,y]`。`agent_fut_cls_scores` 用来给这些 mode 打分。

## ego 规划输出

GenAD 的 ego 输出为：

```plaintext
ego_fut_preds: [B, 3, 6, 2]
```

含义是：

- `3`：三个高层驾驶命令 mode；
- `6`：未来 6 个时间点；
- `2`：每个点为 `[x,y]`。

它和 VAD 一样，不直接输出 heading、速度、加速度，也不输出 `steer/throttle/brake`。训练时会用 `ego_fut_cmd: [B,3]` 选择当前样本对应的命令 mode 计算规划损失。

# TCP

TCP 是 CARLA 系端到端方法里比较特殊的一类：它不是只输出轨迹，也不是只输出控制，而是同时保留 **trajectory branch** 和 **control branch**。轨迹分支输出 waypoints，再由 PID 控制器转成车辆控制；控制分支直接预测一个低层动作分布。最后两条路径在推理时融合。

> 💡 TCP 更接近狭义端到端，因为它确实有 direct control 分支。但它并没有放弃轨迹接口，最终控制来自轨迹控制和直接控制的结合。

## 输入

TCP 的输入包括 RGB 图像、当前速度、局部目标点和 CARLA 路由命令：

```plaintext
img
state = [speed, target_point_x, target_point_y, command_onehot(6)]
target_point = [x, y]
```

</tr>
</thead>

<td style="vertical-align: top;">前视 RGB 图像，送入 CNN 感知 backbone。</td>

```plaintext
1(speed) + 2(target_point) + 6(command) = 9
```

## 轨迹分支输出

TCP 的轨迹分支是自回归生成的。配置中：

```plaintext
pred_len = 4
```

模型从零点开始，每一步根据上一步 waypoint 和目标点继续预测下一步，最终得到：

```plaintext
pred_wp: [B, 4, 2]
```

含义是 4 个未来 waypoint，每个 waypoint 是自车局部坐标系下的二维位置 `[x,y]`。这里没有 heading、速度、加速度。

轨迹分支输出后，TCP 会用 PID 控制器计算：

- 横向控制：根据 waypoint 的方向和目标点方向计算 steering；
- 纵向控制：根据相邻 waypoint 间距估计 desired speed，再和当前 speed 比较得到 throttle/brake。

```plaintext
pred_wp: [B,4,2]
        ↓ PID
steer_traj, throttle_traj, brake_traj
```

## 控制分支输出

控制分支直接预测动作分布参数：

```plaintext
mu_branches: [B, 2]
sigma_branches: [B, 2]
```

这两个维度对应动作分布中的两个动作量：

```plaintext
action = [acc, steer]
```

其中 `acc` 是加减速意图，不是车辆实际物理加速度。代码会把它转换成油门或刹车：

```plaintext
if acc >= 0:
    throttle = acc
    brake = 0
else:
    throttle = 0
    brake = abs(acc)
```

因此控制分支最终可以得到：

```plaintext
steer_ctrl
throttle_ctrl
brake_ctrl
```

## 接口小结

```plaintext
输入:
  RGB image
  speed: [B,1]
  target_point: [B,2]
  command_onehot: [B,6]

中间:
  pred_wp: [B,4,2]
  action distribution: mu/sigma [B,2]

输出:
  steer, throttle, brake
```

TCP 因此处在两类端到端之间：它既有 sensor-to-waypoints 的规划端到端，也有 sensor-to-control 的直接控制分支。和 VAD、UniAD 相比，TCP 离低层控制更近；和纯黑盒控制相比，它又保留了明确的 waypoint 中间接口。

# InterFuser

InterFuser 是 CARLA leaderboard 上的传感器融合端到端模型。它的主线是：多相机图像和 LiDAR 输入网络，网络输出 waypoints 和若干交通语义辅助量，然后由专门的安全控制器生成 `steer/throttle/brake`。因此它不是直接把神经网络输出接到车辆控制，而是把网络规划结果和规则/安全约束结合起来。

> 💡 InterFuser 的“端到端”主要体现在传感器到 waypoints 与交通语义的联合预测；最终低层控制仍由控制器完成。

## 输入

InterFuser 的推理输入包含多相机、LiDAR、速度、路线命令和局部目标点：

```plaintext

rgb_left
rgb_right
rgb_center
lidar
measurements
target_point
```

## waypoints 到控制

InterFuser 并不是让网络直接输出方向盘、油门、刹车。代码里会把 `pred_waypoints` 和交通语义结果交给控制器：

```plaintext
controller.run_step(
    velocity,
    pred_waypoints,
    is_junction,
    traffic_light_state,
    stop_sign,
    traffic_meta
)
```

控制器内部会根据 waypoints 计算目标方向和目标速度，同时结合红绿灯、stop sign、路口状态、交通对象风险来决定是否减速、刹停或继续行驶。

```plaintext
steer
throttle
brake
```

因此 InterFuser 的控制链路是：

```plaintext
multi-camera + lidar + route command + speed
        ↓
InterFuser network
        ↓
pred_waypoints + traffic semantics
        ↓
safety / rule-aware controller
        ↓
steer, throttle, brake
```

## 接口小结

```plaintext
输入:
  multi-view RGB
  lidar BEV
  measurements: [command_onehot(6), velocity]
  target_point: [x, y]

网络输出:
  pred_waypoints: [N, 2]
  traffic_meta
  is_junction
  traffic_light_state
  stop_sign
  bev_feature

最终控制:
  steer, throttle, brake
```

InterFuser 的价值在于把多传感器感知、路径跟踪和交通规则相关语义放在一个模型里联合预测；但从执行接口看，它仍然属于 sensor-to-waypoints，再通过控制器到 vehicle control 的路线。
